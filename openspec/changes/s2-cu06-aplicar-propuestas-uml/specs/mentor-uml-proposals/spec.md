## ADDED Requirements

### Requirement: Structured and validatable UML proposal (RF-18)
The system SHALL accept from the assistant only a structured UML proposal intent with a known, closed structure, and SHALL validate and resolve it against the authoritative project document before it can be executed.

#### Scenario: Structured ADD_ATTRIBUTE proposal
- **WHEN** a user with edit access requests "Agrega el atributo teléfono de tipo String a Cliente" and the class `Cliente` exists in the authoritative document
- **THEN** the system SHALL create a `PENDING` proposal whose operation is `ADD_ATTRIBUTE` targeting `Cliente`, with the attribute name preserved as requested after trimming (`teléfono`, without transliteration) and the type resolved to the canonical primitive `string`, and SHALL NOT modify the project
- **AND** the server SHALL resolve the intent against the authoritative project document into exactly one `UmlCommand`, assigning every identifier itself

#### Scenario: Operation outside the allow-list
- **WHEN** the generated intent declares an operation outside the closed allow-list of operations, which in this version SHALL contain only `ADD_ATTRIBUTE`
- **THEN** the system SHALL reject it with `UNSUPPORTED_OPERATION`, SHALL NOT persist a proposal and SHALL NOT modify the project

#### Scenario: The assistant does not provide identifiers
- **WHEN** a generated intent contains identifier fields or extra fields
- **THEN** the system SHALL reject it as `INVALID_PROPOSAL`; class and attribute identifiers SHALL come only from server resolution and server generation
- **AND** a valid intent SHALL reference model elements by name and SHALL NOT contain identifiers

#### Scenario: Server resolves the real element
- **WHEN** the intent names a class that does not exist in the authoritative document
- **THEN** the system SHALL reject it with `ELEMENT_NOT_FOUND` and SHALL NOT create the class or guess another one
- **AND** any intent that cannot be resolved SHALL be rejected without falling back to defaults

#### Scenario: Invalid attribute type
- **WHEN** the intent declares an attribute type that is neither a supported primitive after normalization nor an explicitly supported reference
- **THEN** the system SHALL reject it with `UNKNOWN_TYPE` and SHALL NOT fall back to `string`

#### Scenario: Invalid multiplicity
- **WHEN** the intent declares a multiplicity that the strict parser or the canonical validation does not accept
- **THEN** the system SHALL reject the proposal and SHALL NOT assume a different multiplicity; an absent multiplicity SHALL remain absent

### Requirement: Deterministic preview without modification (RF-19)
The system SHALL compute the preview by executing the persisted resolved command against a disposable copy of the authoritative document with the existing command executor and validators. The diff SHALL be derived deterministically from the documents before and after that execution and SHALL NOT be generated by the assistant. Public diagnostics SHALL contain only code, severity and message.

#### Scenario: Preview shows a deterministic diff
- **WHEN** a valid `ADD_ATTRIBUTE` proposal adding `teléfono: string` to `Cliente` is previewed
- **THEN** the preview SHALL be valid and SHALL contain exactly the diff line `{ kind: "added", element: "attribute", label: "Cliente.teléfono: string" }`, identical across repeated previews of the same proposal and revision

#### Scenario: Preview does not modify the document
- **WHEN** a proposal is created or its detail is read
- **THEN** the project document, layout, revision and receipts SHALL remain exactly as before

#### Scenario: Preview matches the persisted command
- **WHEN** a proposal is previewed and later applied
- **THEN** both SHALL use the same persisted command with the same server-assigned attribute identifier; no identifier SHALL be generated at apply time

#### Scenario: Invalid candidate at creation
- **WHEN** executing the resolved command on the copy is rejected by the canonical validation, for example by a duplicate attribute name
- **THEN** the system SHALL reject the request with `INVALID_PROPOSAL`, SHALL expose the validation diagnostics without internal paths or identifiers, and SHALL NOT persist a proposal

#### Scenario: Detail of a stale proposal
- **WHEN** the detail of a `PENDING` proposal is read after the project revision moved past its base revision
- **THEN** the response SHALL keep the persisted diff, SHALL report the preview as not valid with a `STALE_PROPOSAL` diagnostic, and SHALL NOT recompute the proposal against the newer revision

### Requirement: Explicit developer confirmation (RF-20)
The system SHALL NOT modify the model when a proposal is created, previewed, closed or cancelled. Only an explicit apply request for a persisted proposal from a user with edit access SHALL modify the model, and only if the proposal is `PENDING`, its preview is valid and its base revision equals the current project revision. Closing or cancelling the preview SHALL be a client-only action that sends no request and keeps the proposal `PENDING`.

#### Scenario: Creating a proposal does not apply it
- **WHEN** a proposal is created
- **THEN** its status SHALL be `PENDING` and the project revision SHALL be unchanged

#### Scenario: Closing or cancelling does not modify
- **WHEN** the user closes or cancels the preview
- **THEN** no server request SHALL be sent, the model SHALL remain exactly as before and the proposal SHALL remain `PENDING`

#### Scenario: Apply requires an explicit action
- **WHEN** the user confirms with the apply action
- **THEN** the client SHALL send only the proposal identifier, without operation, command, base revision or diff, and the server SHALL use only the persisted proposal

#### Scenario: VIEWER cannot confirm
- **WHEN** a VIEWER requests to create, read the detail of, apply or reject a proposal
- **THEN** the system SHALL respond 403 and SHALL NOT modify the model or the proposal; a user without access to the project SHALL receive 404

#### Scenario: Stale proposal is not applied
- **WHEN** a proposal captured `baseRevision = 10` and the project is now at revision 11
- **THEN** applying it SHALL fail with `STALE_PROPOSAL` (HTTP 409), SHALL NOT be regenerated or rebased automatically, SHALL NOT modify the model and the proposal SHALL remain `PENDING`

### Requirement: Execution through existing commands and recorded result (RF-21)
The system SHALL execute a confirmed proposal only through the existing project operation mechanism (`ProjectOperationService.apply`) and SHALL record the result of its resolution on the persisted proposal.

#### Scenario: Apply uses the existing mechanism
- **WHEN** a valid `PENDING` proposal is applied
- **THEN** the change SHALL be executed by `ProjectOperationService.apply` with the existing edit authorization, per-project queue, revision control and operation receipt
- **AND** the call SHALL use `operationId` equal to the proposal identifier, the persisted project, the persisted base revision and the persisted command, and the system SHALL NOT write the project document directly
- **AND** the change SHALL be observable by connected collaborators like a normal editor operation

#### Scenario: Exactly one valid revision
- **WHEN** an `ADD_ATTRIBUTE` proposal is applied at revision N
- **THEN** the project SHALL be at revision N + 1 containing exactly the previewed attribute, and the proposal SHALL record `resultingRevision = N + 1`

#### Scenario: Double apply does not duplicate the change
- **WHEN** the same proposal is applied twice, concurrently or sequentially
- **THEN** the model SHALL change at most once and the later request SHALL receive `PROPOSAL_ALREADY_APPLIED` (HTTP 409) or the same recorded result

#### Scenario: APPLIED records the result
- **WHEN** an application succeeds
- **THEN** the proposal SHALL be `APPLIED` with `resolvedAt`, the resolving user and `resultingRevision`, and later apply or reject requests SHALL fail with `PROPOSAL_ALREADY_APPLIED`

#### Scenario: REJECTED does not modify UML
- **WHEN** an OWNER or EDITOR rejects a `PENDING` proposal
- **THEN** the proposal SHALL become `REJECTED` with `resolvedAt` and the resolving user, the model and revision SHALL remain unchanged, and a later apply SHALL fail with `PROPOSAL_REJECTED` (HTTP 409)
- **AND** `APPLIED` and `REJECTED` SHALL be terminal

#### Scenario: Another project cannot access the proposal
- **WHEN** a proposal identifier is requested under a different project, or by a user without access to the proposal's project
- **THEN** the system SHALL respond 404 and SHALL NOT reveal whether the proposal exists

#### Scenario: Result available for the shared history
- **WHEN** a proposal is created, applied or rejected
- **THEN** its identifier, status, diff summary, creation time and resolution time SHALL remain persisted per project so that CU-2P-07 can later expose a read projection with view access
